7 Front-End Performance Habits That Actually Move the Needle in 2026

September 18, 20266 min read

Every client asks for a "fast website." Almost none of them can tell me what that means in numbers — and honestly, most developers I talk to can’t either. They’ll compress an image, feel good about it, and move on. Here are the seven checks I actually run on every project before it ships, in the order I run them.

1. Measure before you optimize anything

This sounds obvious and almost nobody does it. Before I touch a line of code, I run the live site through Lighthouse and PageSpeed Insights and write down the actual Core Web Vitals numbers — Largest Contentful Paint, Cumulative Layout Shift, and Interaction to Next Paint. Optimizing without a baseline means you can’t tell a client whether anything you did actually helped, and half the time it turns out the thing you assumed was slow wasn’t the bottleneck at all.

2. Ship fonts that don’t block rendering

Custom fonts are the single most common cause of layout shift I see on small business sites. The fix isn’t complicated: use font-display: swap so text renders in a fallback font immediately, preconnect to your font host, and self-host your fonts if you can — it removes a DNS lookup and gives you full control over caching. On this site I use two font families and both are preconnected before anything else loads.

3. Treat images as a budget, not an afterthought

A single unoptimized hero image can undo everything else you did right. My rule: WebP or AVIF first with a JPEG fallback, explicit width and height attributes so the browser reserves space before the image loads, and loading="lazy" on anything below the fold. For a grocery delivery client I recently reduced their homepage image payload from 4.2MB to under 900KB just by re-encoding what was already there — no redesign required.

The fastest asset is the one you never send. The second fastest is the one you send once and cache forever.

4. Cache aggressively, then invalidate on purpose

Static assets — CSS, JS, fonts, images that don’t change — should carry long Cache-Control headers with content-hashed filenames, so a returning visitor's second page load costs almost nothing. The mistake I still see constantly is a blanket "no-cache" rule slapped on an entire site because one HTML page needed to update frequently.

5. Defer anything that isn’t the first paint

Chat widgets, analytics scripts, social embeds — none of them need to load before your hero section is visible. I load third-party scripts with defer or after the load event fires, and for anything genuinely optional (a review widget, a cookie banner library) I’ll load it only once the user scrolls near it. It routinely shaves half a second or more off Time to Interactive on marketing sites.

6. Don’t ship a framework you don’t need

A five-page brochure site does not need a client-side router, a state management library, and 300KB of JavaScript before it can show a headline. This portfolio and the sites I build for most small business clients are plain HTML, CSS and a small amount of vanilla JavaScript — not because frameworks are bad, but because the performance budget of a marketing site is different from the performance budget of an application.

7. Re-test on a throttled connection, not your fiber line

Everything looks fast on a developer machine with a gigabit connection. Chrome DevTools has a "Slow 4G" throttling preset for a reason — a meaningful share of visitors in markets like Bangladesh are on exactly that kind of connection, and a site that feels instant to you might take four or five seconds to become usable for them. I test every project this way before calling it done.

None of these seven habits are exotic. What matters is doing all of them, consistently, on every project — not just the ones a client specifically asks about.
